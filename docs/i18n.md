# i18n 规范（多语言开发与验收清单）

> 本规范定义 sgai 项目支持多语言（当前 zh + en + ja + zh-tw + ko 五语）的方式。新增页面、新增数据、改动共享组件，全部按本规范执行；提交前必须通过 `npm run check:dist` 验证。
>
> Last updated: 2026-05-24

## 0. 五语状态速览（2026-05-23 引入 zh-tw + ko）

| Lang | URL | HTML lang | 数据字段 | UI 字典 | 状态 |
| --- | --- | --- | --- | --- | --- |
| `en` | `/` (no prefix) | `en` | `*En` 必填 | 280 keys 完整 | 全站 ✓ |
| `zh` | `/zh/` | `zh-CN` | 裸字段（默认） | 280 keys 完整 | 全站 ✓ |
| `ja` | `/ja/` | `ja` | `*Ja` 必填（gate 强制） | 280 keys 完整 | 全站 ✓ |
| `zh-tw` | `/zh-tw/` | `zh-Hant` | **不存储**（运行时 OpenCC s2twp 转换） | 仅 override（`zhTwDict`） | 全站 ✓ (1028 pages, 0 residue) |
| `ko` | `/ko/` | `ko` | `*Ko` 必填（gate 强制） | 280 keys 完整（haiku 翻译 seed） | 全站 ✓ |

**zh-tw 不需要 `*ZhTw` 数据字段**——`pickLocalized` 命中 zh 兜底时自动跑 OpenCC s2twp（Simplified→Traditional with Taiwan idiom substitution: 软件→軟體、视频→影片、信息→資訊、程序→程式、鼠标→滑鼠）。详见 [src/i18n/opencc.ts](../src/i18n/opencc.ts)。零数据膨胀、零 drift bug、零 API 翻译成本。手动 override 走 `zhTwDict` 字典或 `*ZhTw` 字段（命中优先级高于 OpenCC）。

**ko 需要 `*Ko` 数据字段**——UI 字典与数据层用户可见字段都必须补齐。缺失 `*Ko` 不能靠 fallback 混过去；`npm run check:i18n-completeness`、`pre-commit`、`pre-push` 都会失败。

**OpenCC 边界 case**：`src/i18n/opencc.ts` 内置了 ~20 条 post-process 补丁（`后续→後續` 之类的常见 mmseg 分词错位）。新发现 OpenCC 误转的 case，往 `POST_DICT` 加一行即可。验证：`npx tsx -e "import { toTraditional } from './src/i18n/opencc'; console.log(toTraditional('你的字符串'));"`。

## 1. 站点基本架构

- 默认路由语言 `en`（不带前缀，`/`、`/policies/`），其他语言一律加前缀（`/zh/...`、`/ja/...`、`/zh-tw/...`、`/ko/...`）。
- 默认**内容**语言是 `zh` —— 数据文件裸字段（`title` / `description` ...）默认存中文。其他语言用 `*<Cap-Lang>` 兄弟字段：`titleEn`、`titleJa`、`titleKo`（zh-tw 不存数据，运行时 OpenCC 转换）。
- 动态路由页：`src/pages/[lang]/<route>/<file>.astro` 一次涵盖所有非默认 locale，`getStaticPaths` emit 来自 `NON_DEFAULT_ROUTE_LOCALES`。Markdown 博客文件用 `src/data/post/<slug>.md`（zh）与 `src/data/post/<lang>/<slug>.md`（其他语言）。
- 所有 i18n 工具函数集中在 [src/i18n/index.ts](../src/i18n/index.ts)：
  - `LOCALES: Lang[]` / `DEFAULT_LOCALE: Lang` / `ROUTE_DEFAULT_LOCALE: Lang` — 当前激活的语言、内容默认、路由默认
  - `getLangFromPath(pathname)` → 当前语言（不识别的前缀回落 default）
  - `localePrefix(lang)` → `''`（路由默认）或 `'/<lang>'`
  - `localizedHref(path, lang)` → 给绝对路径加 lang 前缀
  - `unprefixed(path)` → 去掉任意 lang 前缀，恢复 canonical 默认语言路径
  - `pickLocalized(record, baseKey, lang)` → **新形态（推荐）**，N 语言通用，zh-tw 自动跑 OpenCC
  - `pickLocalized(record, zhKey, enKey, lang)` → 旧形态（保留兼容，仅限 zh+en）
  - `channelLabel(channel, lang)` → SocialChannel 的显示文本
  - `t(lang, key)` → 字典查询（zh 字典是真值，其他语言缺失时按 fallback 链回落）
  - `IN_LANGUAGES: Record<Lang, string>` → BCP-47 codes for `<html lang>` + hreflang + JSON-LD `inLanguage`
- `Lang` 联合类型: `'zh' | 'en' | 'ja' | 'zh-tw' | 'ko'`。Lang code 本身就是 URL 段（kebab-case 适配带 region 的语言：`zh-tw`、未来 `pt-br` 等）。
- `siblingSuffix`: 按 hyphen 切分后每段首字母大写：`'zh-tw'` → `'ZhTw'`，`'ko'` → `'Ko'`。这就是 `titleZhTw` / `titleKo` 字段名的由来（虽然 zh-tw 当前不需要）。

ja 已于 v0.12.0 完成全站集成（~5,756 条 `*Ja` 字段回填 + 42 个 `/ja/` 页面 + 8 篇日语博客 + 11 条 refresh 管线自动产出 ja 翻译）。

zh-tw + ko 已于 2026-05-23 加入基础设施（v0.13.0），见第 0 节状态表。

### 1.1 新增第六门语言的流程

设你要加 `fr`（法语）：

1. [src/i18n/index.ts](../src/i18n/index.ts): 把 `'fr'` 加进 `Lang` 联合类型 + `LOCALES` 数组
2. 在 `IN_LANGUAGES` 加 `fr: 'fr'`，在 `FALLBACK_CHAINS` 加 `fr: ['fr', 'en', 'zh']`
3. 添加导出 `export const fr: Partial<Record<keyof typeof zh, string>> = { ... }` 字典；注册到 `DICTIONARIES`
4. [Metadata.astro](../src/components/common/Metadata.astro) 的 `OG_LOCALES` 加 `fr: 'fr_FR'`
5. [utils.ts](../src/utils/utils.ts) 的 `FORMATTERS` 加 `fr: new Intl.DateTimeFormat('fr-FR', ...)`
6. [Layout.astro](../src/layouts/Layout.astro) 的 `HTML_LANG` 不需要改（reuse `IN_LANGUAGES`）
7. [LanguageToggle.astro](../src/components/common/LanguageToggle.astro) 的 `LANG_LABELS` 加 `fr: 'Français'`
8. [LangBanner.astro](../src/components/common/LangBanner.astro) 的 `BANNER_MESSAGES` + `SWITCH_LABELS` 加 fr 入口
9. 复制 `scripts/i18n/build-ko-dict.ts` 改名为 `build-fr-dict.ts`，跑 `npx tsx scripts/i18n/build-fr-dict.ts > scripts/i18n/data/fr-dict.txt`；splice 进 `src/i18n/index.ts` 的 `fr` 字典
10. [scripts/i18n-check.mjs](../scripts/i18n-check.mjs) 的 `LANG_CONFIG` 加 `fr` 配置（foreign-script regex + allow patterns）；否则 `check:i18n:all` 会因为新语言缺 dist 检查配置而失败
11. `npm run check && npm run build && npm run check:dist` 验证

一旦 `fr` 加进 `LOCALES`，它就是正式语言，不再是"可选翻译"。`check:i18n-completeness` 会自动把 `fr` 纳入 sibling 列表，配置字段和通用 alignment 字段缺 `*Fr` 都会 hard-fail。只有显式登记为派生语言（类似 `zh-tw`）的 locale 才不要求数据 sibling。

### 1.2 zh-tw 特殊：运行时 OpenCC 转换

zh-tw 不走传统"加字段+回填"流程。架构上，`pickLocalized` 和 `t()` 命中 zh 兜底（FALLBACK_CHAINS: `'zh-tw': ['zh-tw', 'zh']`）时，自动对返回值跑 `toTraditional()`（[src/i18n/opencc.ts](../src/i18n/opencc.ts)），输出 Taiwan-idiom Traditional。

副作用：
- **零数据膨胀**：不需要 `*ZhTw` 兄弟字段
- **零 drift bug**：zh 改了 zh-tw 自动跟上
- **零 API 翻译成本**：OpenCC 是本地决定性词典
- **不完美的边界 case**：mmseg 分词偶尔出错（如 `球后续` 被切成 `球后/续`），靠 [opencc.ts](../src/i18n/opencc.ts) 里 `POST_DICT` 做 ~20 条后处理补丁兜底。发现新边界 case 加一行即可。

什么时候要手动 `*ZhTw` 覆盖？三种情况：
1. 品牌/专有名词（`新加坡 AI 观察` 不能机械转换）—— 在 `zhTwDict` 字典里覆盖
2. 标题 / 长描述里有跨地区语义差异 —— 数据文件加 `titleZhTw` 字段
3. OpenCC 误转的高曝光内容（首页 hero / nav）—— `zhTwDict` 优先级最高

## 2. 数据契约（双字段约定）

> 一句话：数据文件以中文为主语言，其他 authored 语言以 `*<Cap-Lang>` 兄弟字段并列存储；展示由页面 + `pickLocalized` 决定。

### 2.1 命名规则

- 默认语言（zh）字段用裸名：`title`、`description`、`summary`、`role`...
- 其他 authored 语言加 capitalized 后缀：`titleEn`、`titleJa`、`titleKo`、`descriptionEn`、`descriptionJa`...
- 数组字段同样加后缀：`keyDebates: string[]` ↔ `keyDebatesEn?: string[]`。
- TypeScript 接口里非默认语言字段都标 `?` 可选。

```typescript
export interface KeyInsight {
  title: string;
  titleEn?: string;
  titleJa?: string;
  titleKo?: string;
  description: string;
  descriptionEn?: string;
  descriptionJa?: string;
  descriptionKo?: string;
  evidence: string;
  evidenceEn?: string;
  evidenceJa?: string;
  evidenceKo?: string;
  significance: 'high' | 'medium' | 'low';
}
```

### 2.2 例外：标题已是英文的字段

某些数据 `title` 字段本身存的是英文（例如国会辩论 Hansard 原始标题）。此时 `zhTitle` 是中文兄弟字段。这种"英文为主+中文翻译"的反向布局允许存在，但所有页面渲染时**仍然走 `pickLocalized`**，不要假设方向。

### 2.3 状态枚举值

`status: '已落实' | '进行中' | '仍在讨论'` 这种枚举型字符串，比较用原值（中文），但**展示给用户的字符串要在页面层做翻译映射**。具体可参考 `src/pages/en/debates/index.astro` 的 `statusLabels`。

如果将来要彻底干净，把枚举值换成 `'implemented' | 'in-progress' | 'under-discussion'`，再用页面层翻译。当前为兼容历史数据保持中文枚举值。

### 2.4 SocialChannel `label` / `labelEn`

- `label` 默认存 zh（如 `"官网"`、`"MDDI 官网"`、`"@joteo_ylm"`）。
- 若 `label` 含 CJK 字符，**必须**同时给所有 authored locale sibling（如 `labelEn` / `labelJa` / `labelKo`）。
- 平台名（twitter、linkedin、facebook 等）由 `channelLabel()` 内置兜底，不需要逐条写。
- 纯拉丁文标签（`@joteo_ylm`、`Newsletter`）可以把 `labelEn` / `labelJa` / `labelKo` 写成同一个值；不要省略 sibling。显式重复表示这是人工确认的 language-neutral label。

### 2.5 生成型长文本（字幕、transcript、抓取正文）

- 生成型长文本也必须遵守同一套兄弟字段规则，不能因为来源是外部抓取就直接复用到所有语言页面。
- 默认语言字段仍然用裸名，例如视频 transcript 的 `paragraphs` 是中文；英文用 `paragraphsEn`。
- 如果抓到的来源是英文，要先存入 `paragraphsEn`，再翻译成 `paragraphs` 给中文页使用。
- 页面层必须按 lang 选择字段；中文页不得直接把英文 source transcript 当作正文渲染。
- 国会辩论详情页是强约束：英文原文必须直接展开；非英文页面必须额外显示完整译文。中文页展示 `paragraphs`（中文译文）+ `paragraphsEn`（英文原文），英文页只展示 `paragraphsEn`。
- 视频 transcript 有专门检查：`npm run check:video-transcripts`。它已经并入 `npm run check`。
- 国会辩论 transcript 有专门检查：`npm run check:debate-transcripts`。它已经并入 `npm run check`。
- policy / ecosystem / lever / voices 等源码数据字段有强制完整性检查：`npm run check:i18n-completeness`。它已经并入 `npm run check`，并由本地 `pre-commit` / `pre-push` hook 执行。
- 源码模板中的二元分支有强制检查：`npm run eval:source-i18n`。它已经并入 `npm run check`，会阻止新增 `isZh ? ... : ...`、`lang === 'zh' ? ... : ...` 这类让新语言静默掉进英文分支的写法。
- `*En` 加工字段是强纯度约束：不能含中文汉字、日文假名、韩文 Hangul。尤其是"先写中文，再处理成英文"的工作流，不能把源语言残片留在英文 sibling。例外只限 `paragraphsEn` / `transcriptEn` 这类官方 verbatim source 字段，页面层仍必须用 `data-i18n-allow-en` 把它标成二级原文材料。
- speech / policy / ecosystem / lever 等构建页有专门检查：`npm run check:localized-rendering`。它已经并入 `npm run check:dist`。
- **禁止把英文 fallback 当作非英语页面正文**。缺少 `paragraphsJa` / `paragraphsKo` / `contentJa` / `contentKo` 等长文本时，页面应显示该语言的"翻译待补"状态，或只给官方 source link；不能静默渲染英文正文伪装成 ja / ko 页面。
- `data-i18n-allow-en` 只能包裹二级的英文原文 / 官方标题 / source excerpt，不能包裹页面主正文。凡是主正文没有目标语译文，必须让页面状态和检查脚本都能看见这个缺口。

## 3. 页面渲染规则

### 3.1 顶层契约

- 每个 `src/pages/<lang>/...` 页面顶部声明 `const lang = '<lang>' as const;` 并把 `lang={lang}` 传给 `Layout`。
- 每个 zh 页面如果使用了任何接受 `lang` prop 的组件，也要传 `lang`（默认从路径推断，但显式传更稳）。
- 渲染数据字段时，**永远不要**直接 `{record.title}` 当默认语言用。统一用：
  - `pickLocalized(record, 'title', lang)` ← **新形态推荐**，自动按 lang 选 `title` / `titleEn` / `titleJa`
  - 简写 `record.titleEn || record.title` 仅在 EN sibling 几乎总存在时使用，且会限制于双语系统
  - 旧形态 `pickLocalized(record, 'title', 'titleEn', lang)` 保留兼容，但新代码不要写
- 不要写 `isZh ? zh : en` / `lang === 'zh' ? zh : en` 这类二元分支。五语页面必须走 `t(lang, key)`、本地 `Record<Lang, string>` 字典，或 `pickLocalized(record, field, lang)`。

### 3.2 链接

- 跳到内部页面时，永远过一层 `localizedHref(path, lang)`。
- 不要硬编码 `/en/` 前缀；不要硬编码 `/people/...` 这类裸路径。
- 例：`<a href={localizedHref(`/people/${p.id}/`, lang)}>...</a>`

### 3.3 共享组件（zh + EN 都使用）

放在 `src/components/` 下、不分 lang 的组件（Header、Footer、Logo、LangBanner、LanguageToggle、Breadcrumb、AuthorBio、TableOfContents、NextPrevPost、RelatedRail、blog/ListItem、blog/SinglePost），必须**自己**从 URL 推断 lang：

```astro
---
import { getLangFromPath } from '~/i18n';
const lang = getLangFromPath(new URL(Astro.url).pathname);
const isEn = lang === 'en';
---
```

然后所有展示文案、内部链接、字段读取都按 lang 走。

### 3.4 镜像页应是 thin wrapper（v0.6.0 起强制）

> 一句话：任何在多语言下结构相同的页面（首页、about、timeline、人物详情等），**结构必须只存在一份**。每个 lang 的 page 文件只负责 metadata + JSON-LD，body 渲染统一委托给共享组件。

**为什么**：v0.5.0 之前我们把"数据层去重 + 页面层独立"作为分工。结果首页设计迭代两次，EN 都没跟上——`zh` 写的是裸中文字符串、`en` 写的是 `t(lang, ...)`，两份文件长得就完全不像，diff 看不出结构漂移；`i18n-check.mjs` 只查"EN 有没有中文残留"，不查"两边结构是否一致"。漂移是必然，不是意外。

**怎么做**：把页面 body 抽到 `src/components/<area>/<PageName>.astro`，接收 `lang: Lang` prop。两个 page 文件都引入同一个组件，各自只填自己的 metadata。

参考实现 — 首页：

- 共享组件：[`src/components/home/HomePage.astro`](../src/components/home/HomePage.astro)
- ZH 包装：[`src/pages/index.astro`](../src/pages/index.astro)（~40 行）
- EN 包装：[`src/pages/en/index.astro`](../src/pages/en/index.astro)（~40 行）

包装文件模板：

```astro
---
import Layout from '~/layouts/PageLayout.astro';
import JsonLd from '~/components/common/JsonLd.astro';
import MyPage from '~/components/<area>/MyPage.astro';
import { t } from '~/i18n';

const lang = 'zh' as const; // or 'en' as const

const metadata = { title: t(lang, 'siteName'), description: t(lang, 'siteDescription') };
const websiteSchema = { '@context': 'https://schema.org', '@type': 'WebSite', /* ... */ };
---

<Layout metadata={metadata} lang={lang}>
  <JsonLd schema={websiteSchema} />
  <MyPage lang={lang} />
</Layout>
```

共享组件内部规则：

- 所有用户可见文案走 `t(lang, key)` 字典；不要嵌任何裸字符串
- 数据字段走 `pickLocalized(record, baseKey, lang)`
- 内部链接走 `localizedHref(path, lang)`
- 不要在共享组件里 `if (lang === 'zh') ... else ...` 分支结构差异——结构必须一致，差异只在文案

**适用范围**：

- ✅ 首页、about、timeline、tracker overview 这种镜像页
- ✅ 镜像但只是顺序/排版略有不同的页面——把差异收进字典或参数，仍然走共享组件
- ❌ Markdown 博客文章（`src/data/post/<slug>.md` 与 `src/data/post/en/<slug>.md`）——内容本就是各语言独立写的，沿用现有双文件方案
- ❌ EN 独占或 ZH 独占的页面——没有镜像，自然没漂移问题

**新增镜像页的步骤**：

1. 写共享组件 `src/components/<area>/<PageName>.astro`，body + 顶部 `interface Props { lang: Lang; }`
2. 在 zh 字典里把所有用户可见文案登记成 key，其他 locale 字典补对应翻译
3. 在对应 route 文件放 thin wrapper；动态路由优先用 `[lang]` 覆盖所有非默认语言
4. 跑 `npm run build && npm run check:dist` 确认所有 locale 无残留

**改动镜像页时**：直接改共享组件。**永远不要**只改其中一个 page 文件。如果发现自己在 page 文件里写了任何 body 结构（不只是 metadata），停下来，把它抽到共享组件去。

### 3.5 zh 副字段（zhTitle, zhName, zhEvent, etc.）

- 在 zh 页面：英文条目可保留 zh 翻译做副显示，符合中文阅读体验。
- 在 EN 页面（以及未来的 ja/ko/...）：**完全隐藏** zh 副字段。EN 页面要保持纯英文，不展示中文注音/副标题。一旦在非默认语言页面渲染了 zh 副字段，i18n-check 会报错。
- 这是 v0.5.0 起的新约定（之前曾允许短姓名做注音，已撤销）。

### 3.6 fallback 的边界

fallback 是可用性兜底，不是翻译完成状态。

- 短 label / 专有名词 / 官方英文标题可以 fallback 到英文。
- 页面主标题、摘要、解释性正文、transcript、policy section、ecosystem profile、lever description 这类核心内容，如果数据里已经有目标语字段，页面必须实际渲染该字段。
- 如果没有目标语长文本，不要用英文填充目标语正文。显示目标语的待翻译提示，并保留 official source / English original 作为二级材料。
- 新增或修改 `[lang]` 动态页后，必须跑 `npm run build && npm run check:dist`；`check:localized-rendering` 会在构建产物里验证 ja / ko 关键页是否渲染了已有的本地化字段。

## 4. SEO 与 Metadata

- `<html lang>`：来自 `IN_LANGUAGES`，当前覆盖 zh-CN / en / ja / zh-Hant / ko。已由 `src/layouts/Layout.astro` 统一处理。
- `og:locale`：由 `src/components/common/Metadata.astro` 根据 lang 输出；新增语言时必须补对应 OG locale。
- `og:site_name`：来源是 `src/i18n/index.ts` 字典，不能在页面里硬编码。
- `<title>` 模板：同样走 `src/i18n/index.ts` 字典。
- `description` 兜底：每个页面应自带各语言 description；缺失时回落 `t(lang, 'siteDescription')`。
- `<link rel="alternate" hreflang>`：所有页面自动按 `LOCALES.map` 输出 alternates + `x-default`；新增页面如果走 PageLayout 自动继承，无需重复配置。

## 5. 验证

### 5.1 自动检查（每次构建）

```bash
npm run build
npm run check:dist                 # = check:i18n:all + check:schema + check:localized-rendering
npm run check:i18n-completeness    # 源码层强否决：按 LOCALES 自动检查所有 authored sibling
npm run check:i18n:all             # 扫 LOCALES 中每个语言的外语残留
npm run check:i18n -- --lang ja    # 只扫 dist/ja
npm run check:localized-rendering  # 检查 ja / ko 关键页是否渲染已有本地化字段
```

脚本逻辑：
1. 走 `dist/<lang>/**/*.html`
2. 剥离 `<script>` `<style>` `<head>` 与所有 HTML 属性
3. 按 `LANG_CONFIG[<lang>].foreignRegex` 搜索"不该出现的脚本"（EN 会同时拦截中文汉字、日文假名、韩文 Hangul）
4. 对照 `LANG_CONFIG[<lang>].allowPatterns` 白名单
5. 命中即报错并定位到具体页面

`check:localized-rendering` 是第二层 gate：它不只看"有没有不该出现的文字"，还会对照 `policies.ts` / `ecosystem.ts` / `levers.ts` / `voices.ts` / `speech-transcripts.ts`，确认 ja / ko 关键详情页实际包含已有的 `*Ja` / `*Ko` 字段；同时禁止 ja / ko speech 页面把英文 transcript 段落当正文渲染。

`check:i18n-completeness` 是源码层强否决项：语言清单从 [src/i18n/index.ts](../src/i18n/index.ts) 的 `LOCALES` 读取。`zh` 是源语言，检查裸字段；`zh-tw` 是派生语言，靠 OpenCC + dist residue gate；其他当前 / 未来 locale 都必须有 sibling（当前 `En` / `Ja` / `Ko`），且不能是空值或占位符。`required: true` 表示源字段本身也必须存在；未标 required 的字段可以不存在，但只要任一语言侧出现，就必须补齐源字段和所有 locale sibling。

同一脚本还会对 `src/data/*.ts` 中常见展示字段做通用 sibling alignment 检查；字符串和 `string[]` 都会检查。也就是说，`title`、`summary`、`highlights`、`bullets`、`tags`、`points` 等字段只要出现中文内容，就必须同时有所有 authored locale sibling（当前 `*En` / `*Ja` / `*Ko`；未来新增语言自动加入），否则 `npm run check`、`pre-commit`、`pre-push` 都会失败。

同时，`*En` 字段会做英文纯度检查：只要出现中文汉字、日文假名或韩文 Hangul 就 hard-fail。`paragraphsEn` / `transcriptEn` 是唯一默认例外，因为它们可能是 Hansard / 官方演讲的原文记录，里面偶尔会包含发言人原话中的多语引用；这类内容在页面层必须继续用 `data-i18n-allow-en` 标成 source material，不能伪装成站点自己写的英文正文。

EN 当前白名单（每条都有理由）：
- `中文版可用` / `阅读中文版` / `中`：LangBanner 与 LanguageToggle 邀请用户切换到 zh 的副本。

如果你为某条特殊残留申请例外，**必须**在 `LANG_CONFIG[<lang>].allowPatterns` 里加注释说明原因。

### 5.2 zh / zh-tw 检查边界

`check:i18n:all` 已经包含 `zh` 和 `zh-tw`。`zh` 页会检查日 / 韩脚本残留；不检查英文残留，因为 zh 页面天然允许英文人名、机构缩写、产品名。`zh-tw` 页会检查 Simplified-only 字符残留，防止绕过 OpenCC 或新增硬编码简体。

## 9. 数据层批量翻译（新增 authored locale）

新增 authored locale 后，数据文件里的 `*<Locale>` 字段必须补齐。一次性脚本按域跑：

```bash
# 模板（基于 scripts/i18n/build-ja-dict.ts 的批量回填模式）：
# - 读 src/data/<domain>.ts
# - 对每条 record 的 title / description / summary 等 CJK 字段
# - 调 translateBatch({ direction: 'zh→<locale>' })，写 title<Locale> / description<Locale>
# - sha256 缓存（重跑零成本）
# - 写回 .ts 文件

# 建议按这个顺序回填（高曝光优先）：
# 1. policies.ts        — 约 80 条
# 2. levers.ts          — 约 30 条
# 3. debates.ts         — 约 100+ 条（content 长）
# 4. ecosystem.ts       — 约 60 条

# 7. videos.ts          — 约 60 条
# 8. tracker.ts         — 约 40 条
# 9. talent.ts          — 约 30 条
# 10. startups.ts       — 约 50 条（含 autoDiscovered[]）
```

跑完后用 `npm run check:i18n-completeness` 验证字段配对。这个 gate 的 locale 列表来自 `LOCALES`，不是手写参数；新增语言不会被漏掉。
